## 核心矛盾

当前的数据流是**串行依赖**：

```
CullingSystem → CullingResult
       ↓
LODSystem → LODResult  
       ↓
各构建器 (串行或等待这些结果)
```

如果要并行化，瓶颈在于 `CullingResult` 和 `LODResult` 成了共享的"中间产物"。

## 改造方向

### 方向一：每个构建器独立做剔除和 LOD（完全自包含）

**做法**：
- 取消全局 `CullingSystem` 和 `LODSystem`
- 每个构建器内部遍历自己关心的组件，**同时**完成剔除和 LOD 选择
- 构建器之间完全独立，可以并行

**优点**：
- 最大并行度，无等待
- 数据局部性好（构建器只碰自己需要的组件类型）

**缺点**：
- 剔除计算重复（同一个实体可能被多个构建器重复做视锥测试）
- LOD 计算重复
- 如果有遮挡查询等昂贵操作，浪费明显

**适用场景**：组件类型隔离度高、构建器数量少、剔除成本低

---

### 方向二：剔除/LOD 结果按需计算 + 缓存（Lazy + Cache）

**做法**：
- 每个实体的可见性/LOD 结果缓存在一个"每帧临时结构"中
- 构建器首次访问某实体时，触发计算并缓存
- 后续构建器直接读缓存

```cpp
struct PerFrameEntityData {
    bool isVisible;
    GeometryHandle lodGeometry;
    bool computed; // 是否已计算
};
```

**优点**：
- 每个实体只计算一次
- 构建器可以并行，计算时加锁或原子操作

**缺点**：
- 需要处理线程安全（细粒度锁或原子状态）
- 缓存管理开销

---

### 方向三：Job 化 + 结果广播

**做法**：
- 保持独立的 `CullingSystem` 和 `LODSystem`，但并行执行
- 剔除系统按实体分区并行（每个 Job 处理一批实体）
- 完成后，生成一个**按实体索引的可查询结构**（数组或位集）
- 所有构建器**只读**这个结构，无需等待系统完成？不，它们还是要等

**关键改进**：
- 将 `CullingResult` 和 `LODResult` 合并成**按实体索引的紧凑数组**
- 构建器启动时，等待的是**整个数组就绪**（屏障），而不是串行依赖
- 这个等待可以在任务图中表达（如 `JobGraph`）

---

### 方向四：构建器流水线 + 帧延迟容忍

**做法**：
- 当前帧的剔除结果用上一帧的
- 构建器用上一帧的可见性本帧开始构建
- 剔除系统本帧计算下一帧的结果

**优点**：
- 完全无等待
- 剔除和构建完全并行

**缺点**：
- 延迟一帧（对于快速移动的物体，可能出现"尸体"或"突然出现"）
- 需要处理可见性变化的平滑过渡

**适用场景**：相机移动相对平滑、没有快速传送

---

## 推荐演进路径

考虑到你已经有多个构建器（Opaque、Transparent、Terrain、Billboard），建议：

**第一阶段**（最小改动，立即见效）：
- 保持现有 `CullingResult` 和 `LODResult`
- 将它们改成**按实体索引的扁平数组**（Entity → 数据）
- 构建器可以**并行读取**（只读，无锁）

**第二阶段**（进一步并行）：
- 剔除和 LOD 系统内部并行（Job 处理实体切片）
- 构建器在任务图中与剔除/LOD 并行？实际上构建器依赖结果，所以顺序无法打破

**第三阶段**（最终形态）：
- 引入**帧延迟**或**双缓冲结果**
- 剔除/LOD 系统每帧计算**下一帧**的结果
- 构建器使用**上一帧计算好**的结果
- 构建器与剔除系统完全并行，只在帧边界交换数据

大型游戏引擎（如 UE5）的可见性系统本质就是方向三 + 方向四的混合：多线程并行剔除 + 结果缓存 + 某些情况下的延迟反馈。



你的调度器已经采用了**双缓冲/延迟一帧**的设计，这正是大型引擎的核心模式。

## 当前调度器分析

```cpp
// FrameDriver::Tick()
ExecutePhase(TaskPhase::Render);     // 渲染上帧数据
ExecutePhase(TaskPhase::EarlyUpdate);
ExecutePhase(TaskPhase::Update);
ExecutePhase(TaskPhase::PreRender);  // 剔除（当前帧）
FrameSync();                         // 冻结当前帧 → 下一帧渲染
```

**关键观察**：
- `PreRender` 阶段的剔除结果，要等到**下一帧**的 `Render` 阶段才被使用
- 这就是天然的**延迟一帧**，剔除和渲染完全解耦

这意味着你的系统**已经具备了大型引擎的帧级并行基础**。

## 大型引擎的剔除模式

| 层级 | 时机 | 执行者 | 粒度 |
|------|------|--------|------|
| 预计算遮挡 | 离线/加载时 | CPU | 场景块 |
| CPU 粗剔除 | PreRender | Job 系统 | 实体级 AABB |
| GPU 细剔除 | Render 阶段开始时 | GPU (Compute Shader) | 实例级/顶点级 |

## 针对万级实体的改造方向

### 1. CPU 粗剔除（当前可用）

保留现有 `CullingSystem`，但改为：
- **分区并行**：将实体列表切分成 Job，每个 Job 处理一批实体的视锥体测试
- **输出位集**：`std::vector<bool>` 或 `std::bitset` 扁平结构，而非 `std::vector<Entity>`
- **后续构建器只读位集**：无锁，O(1) 查询

```cpp
// 输出改为扁平数组
struct CullingResult {
    std::vector<bool> visible;  // index → visible
    std::vector<uint32_t> generation;  // 验证复用
};
```

### 2. 预计算遮挡 + 动态划分

方向：
- **预计算**：编辑器离线计算静态场景的 PVS (Potentially Visible Set)
- **动态划分**：运行时将世界划分为网格/八叉树
- **剔除流程**：视锥体 → 网格单元 → 单元内实体

你的 `TerrainManager` 已经按块加载，可以扩展为网格划分的基础。

### 3. GPU 细剔除（Render 阶段）

```cpp
// Render 阶段开始时
ExecutePhase(TaskPhase::Render);  // 在这里：
    // 1. 执行 Compute Shader 做 GPU 剔除
    // 2. 输出 Indirect Draw 参数
    // 3. 执行绘制
```

GPU 剔除适合：
- 大量实例化物体（草丛、树木、粒子）
- 复杂遮挡（深度缓冲回读）
- 你的 `BillboardRenderItemBuilder` 已经是合批实例，很适合 GPU 剔除

### 4. 利用现有延迟架构优化

既然你已经延迟一帧，可以：

```
帧 N (PreRender):
  - 剔除结果 R(N)
  - 写入双缓冲槽 A

帧 N+1 (Render):
  - 读取槽 A 的剔除结果 R(N)
  - GPU 执行（可能再做一个 GPU 细剔除）

帧 N+1 (PreRender):
  - 剔除结果 R(N+1)
  - 写入双缓冲槽 B
```

剔除系统有**一整帧的时间**完成，无需担心性能。

## 推荐演进路径

| 阶段 | 改动 | 收益 |
|------|------|------|
| 1 | `CullingResult` 改为扁平位集 | 构建器 O(1) 查询，无锁 |
| 2 | `CullingSystem` 内部并行（切分实体列表） | 利用多核 |
| 3 | 引入空间划分（网格/八叉树） | 剔除成本从 O(N) 降到 O(N^(2/3)) |
| 4 | 静态场景预计算 PVS | 完全消除静态物体剔除成本 |
| 5 | GPU 剔除（Compute Shader + Indirect Draw）| 移除实例化物体的 CPU 开销 |

你的调度器架构已经为这些演进提供了基础：延迟一帧 + 任务图 + 渲染阶段分离。只需逐步填充剔除系统的实现即可。
