大型引擎**后期一定会演变成频繁查询某实体的状态**，而且正是这种需求驱动了架构从“每帧清空重建”向“持久化可见性状态”的演进。

## 为什么后期需要频繁查询？

### 1. 遮挡剔除的状态依赖

大型引擎的遮挡剔除算法有一个关键特性：**当前帧的可见性决策依赖于上一帧的查询结果**。

```cpp
// 典型的遮挡剔除逻辑
if (WasVisibleLastFrame) {
    RenderFullMesh();  // 上一帧可见，本帧正常渲染
} else {
    RenderBoundingBoxOnly();  // 上一帧不可见，只渲染包围盒做遮挡查询
}
```

这是因为 GPU 遮挡查询结果是延迟一帧返回的。如果每帧清空状态，这个优化就无法工作。因此引擎必须持久化维护“上一帧是否可见”这个状态，并每帧查询它。

### 2. 分层剔除的数据依赖

大型引擎通常采用多层剔除架构，后面的阶段需要知道前面的结果：

| 剔除阶段 | 输出 | 谁需要查询 |
|---------|------|-----------|
| 视锥剔除 | 粗略可见集 | LOD 系统、遮挡剔除 |
| LOD 选择 | LOD 等级 | 渲染队列构建 |
| 遮挡剔除 | 精确可见集 | 渲染命令生成 |
| 渲染排序 | 绘制顺序 | GPU 提交 |

每个后续阶段都需要查询前一阶段的结果，这不是一次性的数据传递，而是需要在整个 PreRender 阶段随时访问。

### 3. 动态场景的实时更新

大型引擎的剔除系统必须是动态的：

- 动态物体每帧都可能改变位置
- 移动的遮挡物（如车辆、角色）会改变可见性关系
- 需要能够快速查询“哪些物体可能被这个新遮挡物挡住”

## 主流引擎的做法对比

| 引擎 | 可见性存储方式 | 查询模式 |
|------|--------------|---------|
| **Unreal** | `FPrimitiveSceneProxy` 持久存储可见性标志 | 每帧多次查询 |
| **Unity** | `BatchRendererGroup` + SoA 数据布局 | 批量查询 + 逐实例查询 |
| **自研引擎** | 预计算 PVS BitArray + 动态 BitArray | 位操作快速查询 |

Unreal 使用 `FPrimitiveSceneProxy` 持久化存储每个图元的可见性状态，渲染线程每帧多次查询这些标志。Unity 的 BatchRendererGroup 采用 SoA 布局存储剔除数据，通过 Compute Shader 批量查询后，CPU 端仍需要按实例查询结果。

| 系统 | 输入 | 输出 | 与可见性的关系 |

### 🎯 为什么必须组合使用？（以森林场景为例）

假设一个森林场景有 100,000 棵树。最佳的性能方案不是二选一，而是**三管齐下**：

| 优化阶段 | 执行位置 | 核心任务 | 结果（剩余物体） |
| :--- | :--- | :--- | :--- |
| **1. CPU 粗粒度剔除** | CPU (主线程/工作线程) | 剔除不在视锥内的整个**Chunk（区域块）**、被遮挡的大区域 | 100,000 → 10,000 |
| **2. GPU 精细化剔除** | GPU (Compute Shader) | 对剩余 10,000 棵树进行精确的视锥剔除、遮挡查询、距离 LOD 选择 | 10,000 → 3,000 |
| **3. GPU 驱动绘制** | GPU (ExecuteIndirect) | 自动将 3,000 棵树的绘制指令写入 Buffer，硬件直接执行 | 3,000 → 最终 3,000 个 Draw |

### 💡 这种组合的核心优势

1.  **优势一：带宽最优解**
    CPU 遍历 10 万个物体是沉重的负担（需要读取位置、包围盒、状态），但让它处理 1 万个“Chunk”则游刃有余。**CPU 的高速条件分支**和**GPU 的海量并行**在这里完美配合。

2.  **优势二：规避 GPU 的死穴**
    让 GPU 直接处理 100,000 个物体，意味着要建立一个巨大的 `IndirectDraw` 参数缓冲，并持续在 GPU 内存中维护。CPU 粗剔除可以有效控制进入 GPU 环节的数据规模。

3.  **优势三：帧稳定性**
    如果完全依赖 GPU 剔除，在最坏情况下（如视角突然转向），GPU 需要处理海量的物体。而 CPU 粗剔除提供了**保险机制**，确保最差情况下的帧率下限。

### 🏗️ 现代引擎的分层剔除架构（以 UE5 为例）

以 Fortnite 的大战场场景为例（单帧数万个物体），它的剔除流程正是**组合模式**：

-   **第一阶段（CPU）**：**预计算遮挡（Precomputed Visibility）**。利用游戏世界的静态特性，CPU 通过极为廉价的数据查找，直接丢弃 80% 肯定看不见的区域。
-   **第二阶段（CPU）**：**视锥体剔除（Frustum Culling）**。对剩余的物体执行多线程视锥剔除，以极低成本过滤掉视野外的物体。
-   **第三阶段（GPU）**：**遮挡查询（Occlusion Culling）**。将上一帧的数据（或深度缓冲）提交给 GPU 查询，精确找出真正被前方建筑挡住的物体。
-   **第四阶段（GPU）**：**GPU 驱动绘制**。通过 `ExecuteIndirect` 等技术，将确定要绘制的物体进行排序和提交。

最终，CPU 阶段为 GPU 减轻了 90% 的压力，让 GPU 可以专心用它的海量核心完成最后 10% 的精细化工作。

### 💎 总结：该怎么做？

你之前的担忧——剔除和 LOD 是否有用——是完全多余的。它们永远有用。前沿方案的意义在于**转移执行地点，而不是取消必要性**。

所以，你的架构设计中完全可以保留经典的 CPU 多线程剔除，同时向 `ExecuteIndirect` 或 Work Graphs 演进。这会给你带来**最平衡、最可控的性能表现**。
